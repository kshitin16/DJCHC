# Infrastructure Specification — pdf-library-unit

## Deployment

| Facet | Choice | Rationale |
|---|---|---|
| Compute model | One shared Lambda function, backing all four S3-touching resolvers (`getDocumentDownloadUrl`, `createDocumentUploadUrl`, `confirmDocumentUpload`, `deleteDocument`) | Corrected at this stage's review (R-01, R-02): AppSync's direct (VTL/JS) resolvers have no native S3 data source and no AWS SDK access — generating an S3 pre-signed URL (three operations) or issuing an `s3:DeleteObject` call (`deleteDocument`, BR6.4) both require the AWS SDK, which only runs inside actual compute (Lambda). NFR Design's "no Lambda needed, a fast local SDK signing operation" was correct about the operation being fast and local, but wrong about it needing no compute at all — "local" meant no network round trip to S3, not no Lambda invocation. `deleteDocument` needs the identical class of fix: it was originally left as an implicit direct resolver, which cannot call `DeleteObject` any more than a direct resolver could call `getSignedUrl`. One shared Lambda (not four) keeps the IAM surface and cold-start count minimal for four closely-related, low-volume operations. |
| Region | `ap-south-1` (Mumbai) — inherited from auth-unit's Infrastructure Design | One region for the whole project. |
| Networking topology | N/A — no VPC; S3 and DynamoDB are reached via their public AWS service endpoints, IAM-authenticated | No networking layer this Unit configures. |
| Storage strategy | DynamoDB on-demand (`Document` metadata table) + S3 (PDF files) | Matches NFR Design's already-fixed split (metadata vs. file bytes). |
| Environments | Amplify Hosting git-branch model — inherited from auth-unit's Infrastructure Design | Each branch's `Document` table and S3 bucket are provisioned independently per environment. |
| IaC approach | Amplify Gen2 backend-as-code (`amplify/storage/resource.ts` for the S3 bucket, `amplify/data/resource.ts` for the `Document` model) | No separate hand-authored CDK stack. |
| Resource sizing | The one Lambda: 128MB memory (signing/HeadObject calls are lightweight, no image/PDF processing performed in-Lambda), 10s timeout; DynamoDB on-demand and S3 need no capacity planning | Corrected at R-01 alongside the compute-model row — sized to the Lambda's actual light workload (SDK signing calls, one HeadObject for PDF-type verification), not over-provisioned. |

## Infrastructure Services

| Service | Role | Configuration | Notes |
|---|---|---|---|
| `Document` DynamoDB table | Database | On-demand capacity, AWS-managed encryption (NFR4.1) | Amplify Data-generated. |
| S3 bucket | Object store — PDF files | `BlockPublicAccess.BLOCK_ALL` (Q1, NFR Design — the setting that makes the download-URL expiration control actually meaningful), SSE-S3 default encryption, Versioning OFF (committed, per BR6.4's hard-delete semantics), lifecycle rule: `AbortIncompleteMultipartUpload` after 7 days | Every read/write goes through a pre-signed URL generated by the Lambda-backed resolver below — no direct bucket access of any kind. |
| Document Lambda (backing `getDocumentDownloadUrl`, `createDocumentUploadUrl`, `confirmDocumentUpload`, `deleteDocument`) | Compute — S3 SDK signing + verification + deletion, plus the `Document` DynamoDB record's own read/create/delete, Lambda-backed AppSync resolver for all four operations (corrected at this stage's review, R-01 and R-02, plus a further IAM correction below) | Upload URL: 15-minute expiration; download URL: 1-hour expiration (both unchanged from NFR Requirements). IAM role: S3 — `PutObject`/`GetObject` (for signing, not actually transferring bytes), `HeadObject`/`DeleteObject`, all scoped to this bucket only. DynamoDB — `GetItem` on `Document` (`getDocumentDownloadUrl(id)` resolves `id` to `s3Key` before it can sign a download URL — Contract 6's `id`-keyed query, not a bare pass-through; `deleteDocument(id)` also needs `GetItem` first, both to check the document exists and to learn its `s3Key` before the S3 removal step), `PutItem` (`confirmDocumentUpload` creates the record after upload verification), and `DeleteItem` (`deleteDocument`'s record removal after S3 succeeds), scoped to this table only (corrected — the Lambda's role previously listed only S3 actions; this Lambda also owns every DynamoDB access its four operations require, not just the S3 side) | `deleteDocument` (BR6.4: remove the S3 file first, then the `Document` DynamoDB record) runs through this same Lambda rather than being left as an implicit, impossible direct resolver. The S3 `DeleteObject` permission was already present (from `confirmDocumentUpload`'s own non-PDF cleanup case) and needed no change; the DynamoDB permissions were the missing half — without `GetItem`, `getDocumentDownloadUrl` has no way to learn which S3 object to sign a URL for given only a `Document.id`, and `deleteDocument` has no way to learn the `s3Key` to remove or confirm the document exists; without `PutItem`, `confirmDocumentUpload` cannot actually create the record it's responsible for; without `DeleteItem`, `deleteDocument` cannot remove the record. Signing calls remain fast/local with no S3 round trip; `HeadObject`/`DeleteObject` (S3) and the three DynamoDB calls are the operations that do reach a live AWS service. `PutItem`'s field values (`title`, `category`) come directly from `confirmDocumentUpload`'s own now-corrected signature (Contract 6 amended at this stage's review — the client re-supplies both, since this API holds no server-side "pending upload" state to remember them from the earlier `createDocumentUploadUrl` call), not from any additional lookup. |

Accepted risk: an S3 object uploaded via `createDocumentUploadUrl` but never confirmed (client abandons the flow, or `confirmDocumentUpload` is never retried after a failure) persists in the bucket indefinitely with no `Document` record and no corrective mechanism beyond a human noticing it directly in the bucket — `listDocuments` never surfaces it, since it reads only `Document` records. Low blast radius (admin-only, low-volume path); not designed around further at this project's scale.

## Shared Infrastructure

| Shared Resource | Owner Unit | Consumer Units | Access Boundary |
|---|---|---|---|
| Cognito User Pool (Contract 1 identity for `uploadedByGoogleId`; Contract 2 admin-group check on upload/delete — BR6.3) | auth-unit | pdf-library-unit | Read-only — pdf-library-unit's resolvers verify the caller's JWT for `createDocumentUploadUrl`/`confirmDocumentUpload`/`deleteDocument`; `listDocuments`/`getDocumentDownloadUrl` require no auth at all (BR6.5, public read). |

No resource in this table is owned by pdf-library-unit and shared outward — the `Document` table and the S3 bucket are both exclusively this Unit's.
