# Infrastructure Specification — reminder-unit

> **Amended at Code Generation (R-04, Critical — accepted at the Infrastructure Design gate, fixed here per the builder's "Fix at Code Generation" decision).** Both `Reminder` and `DeviceToken` are keyed on `id`; `ownerIdentityId` was a plain, unindexed attribute, yet `myReminders`, `deliver-push`, `registerDeviceToken`, and `setRemindersEnabled` all locate rows by `ownerIdentityId`. This amendment adds an `ownerIndex` GSI to both tables, corrects the affected Lambdas' IAM from bare `Query`/`GetItem` to index-scoped `Query`, and updates `myReminders`' sizing to include that Query. The two direct resolvers (`registerDeviceToken`, `setRemindersEnabled`) locate the caller's `DeviceToken` row via `ownerIndex` as well. reminder-unit's Code Generation plan is obligated to implement exactly these indexes and access paths.

## Deployment

| Facet | Choice | Rationale |
|---|---|---|
| Compute model | Six Lambdas: `myReminders`, `snoozeReminder`, `cancelReminder` (mutation/query resolvers that call the EventBridge Scheduler API), Contract 8 event handler (DynamoDB-Streams-triggered), `deliver-push` and `auto-clear` (EventBridge-Scheduler-triggered). `registerDeviceToken`/`setRemindersEnabled` remain plain direct AppSync resolvers (corrected at this stage's review, R-01: `myReminders`' sync path creates two EventBridge schedules per new Reminder — performance-design.md's own NFR-PERF.1 design — which a direct VTL resolver cannot do, the identical constraint that already made `snoozeReminder`/`cancelReminder` Lambda-backed). | Matches NFR Design's already-fixed logical-components.md topology plus this stage's correction — the most compute-heavy Unit in the project. |
| Region | `ap-south-1` (Mumbai) — inherited from auth-unit's Infrastructure Design | One region for the whole project. |
| Networking topology | No VPC — all six Lambdas talk only to DynamoDB, EventBridge Scheduler, and (for `deliver-push`) FCM's public HTTPS API, via public AWS/internet endpoints | No private resource to reach. |
| Storage strategy | DynamoDB on-demand (`Reminder` table with `postIdIndex` and `ownerIndex` GSIs; `DeviceToken` table with `ownerIndex` GSI) | Matches NFR Design's already-fixed split and GSI addition (R-02), plus the two `ownerIdentityId` indexes added by the R-04 amendment below. |
| Environments | Amplify Hosting git-branch model — inherited from auth-unit's Infrastructure Design | Each branch's two tables, six Lambdas, and EventBridge Scheduler group are provisioned independently per environment. |
| IaC approach | Amplify Gen2 backend-as-code — `amplify/data/resource.ts` for both tables and the two remaining direct resolvers (`registerDeviceToken`, `setRemindersEnabled`); `amplify/functions/my-reminders/resource.ts`, `amplify/functions/snooze-reminder/resource.ts`, `amplify/functions/cancel-reminder/resource.ts`, `amplify/functions/reminder-stream-handler/resource.ts` (Contract 8), `amplify/functions/deliver-push/resource.ts`, `amplify/functions/auto-clear/resource.ts` | No separate hand-authored CDK stack. |
| Resource sizing | `myReminders`: 128MB/10s (one `listPosts` call, one `Query` on `Reminder`'s `ownerIndex` for the caller's existing reminders — added by the R-04 amendment — a bounded backfill loop over new Event posts, one DynamoDB write plus two `CreateSchedule` calls per new Reminder — performance-design.md's own NFR-PERF.1 budget). `snoozeReminder`/`cancelReminder`: 128MB/5s each (one `GetItem`, one conditional write, one or two fast EventBridge API calls — performance-design.md's own latency budget). Contract 8 handler: 128MB/10s (one GSI Query + a bounded number of cancel/schedule-delete operations per stream record). `deliver-push`: 128MB/10s (one GetItem on `Reminder`, one `Query` on `DeviceToken`'s `ownerIndex` — R-04 amendment — one FCM HTTP call). `auto-clear`: 128MB/5s (one GetItem, one conditional status update). | All six are single-item or small-bounded-loop operations at this app's volume (a handful of syncs/fires per day) — no Scan, no unbounded loop, no reason to size beyond the light default. |

## Infrastructure Services

| Service | Role | Configuration | Notes |
|---|---|---|---|
| `Reminder` DynamoDB table | Database | On-demand capacity, AWS-managed encryption (NFR4.1). GSI `postIdIndex`: partition key `postId`, no sort key (NFR Design R-02). **GSI `ownerIndex`: partition key `ownerIdentityId`, sort key `initialFireAt`** (R-04 amendment) | Amplify Data-generated. `postIdIndex` backs only the Contract 8 handler's one-to-many lookup; `ownerIndex` backs `myReminders`' "all of this device's reminders" lookup — the table's key is `id`, so without it that zero-argument query has no efficient path and would degrade to a Scan. The fire/clear delivery paths use neither index (performance-design.md). |
| `DeviceToken` table | Database | On-demand capacity, AWS-managed encryption (NFR4.1). **GSI `ownerIndex`: partition key `ownerIdentityId`, no sort key** (R-04 amendment) | Amplify Data-generated. `ownerIndex` is how `deliver-push` resolves the device's push token from a Reminder's `ownerIdentityId`, and how `registerDeviceToken`/`setRemindersEnabled` locate the caller's existing row — the table's key is `id`, unrelated to the identity, so `GetItem` cannot do any of these. |
| `myReminders` Lambda | Compute — sync/backfill query resolver (added at this stage's review, R-01) | 128MB/10s. IAM: `Query` on `Reminder`'s `ownerIndex` GSI (by `ownerIdentityId`, the caller's own guest identity — index-scoped, R-04 amendment), `PutItem` on `Reminder` (backfill writes for new Event posts), `CreateSchedule` (fire- and auto-clear-schedules, two per new Reminder) scoped to this Unit's own EventBridge Scheduler group | Direct AppSync resolvers cannot call `CreateSchedule` — the same constraint that already made `snoozeReminder`/`cancelReminder` Lambda-backed applies here, since `myReminders`' sync path is the operation that actually creates each new Reminder's two delivery schedules (performance-design.md NFR-PERF.1). Also calls `listPosts` (Contract 3, feed-unit) via the shared AppSync API, not a direct table read. |
| `snoozeReminder`/`cancelReminder` Lambdas | Compute — mutation resolvers | 128MB/5s each. IAM: `GetItem` on `Reminder` (to read current status before deciding the transition/no-op branch — reliability-design.md's BR7.3/BR7.10 logic, corrected at this stage's review, R-02) plus `UpdateItem` on `Reminder` (by `id`), plus `UpdateSchedule` (`snoozeReminder`, fire-schedule only) or `DeleteSchedule` (`cancelReminder`, both fire- and auto-clear-schedules) scoped to this Unit's own EventBridge Scheduler group | Matches security-design.md's least-privilege intent exactly — no table-wide access, no wildcard Scheduler-group access. `GetItem` was the missing half: BR7.3/BR7.10's status-dependent branching (real transition vs. idempotent no-op re-sync vs. plain no-op) cannot be decided without reading the Reminder's current status first. |
| Contract 8 event handler Lambda | Compute — DynamoDB-Streams-triggered | 128MB/10s. Trigger: `Post` table's stream (feed-unit's resource, consumed here — Contract 8). IAM: `Query` on `Reminder`'s `postIdIndex` GSI (scoped to that index, not table-wide Scan), `UpdateItem` on `Reminder`, `DeleteSchedule` on this Unit's Scheduler group | Reacts to `PostDeleted` (BR7.9) only — `PostDateTimeChanged`/BR7.8 was simplified to a no-op at NFR Design and needs no handler action. |
| `deliver-push` Lambda | Compute — EventBridge-Scheduler-triggered | 128MB/10s. IAM: `GetItem` on `Reminder` (by `id`), `Query` on `DeviceToken`'s `ownerIndex` GSI (by the Reminder's `ownerIdentityId`, to resolve the push token — R-04 amendment; `GetItem` was wrong because `DeviceToken`'s key is its own `id`), plus permission to call FCM's HTTP v1 API using a Firebase service-account credential (Secrets Manager, below) | Emits the delivery-timing custom metric (observability-design.md) by comparing invocation time against the Reminder's `initialFireAt`/`snoozeFireAt`. |
| `auto-clear` Lambda | Compute — EventBridge-Scheduler-triggered | 128MB/5s. IAM: `GetItem`/`UpdateItem` on `Reminder` (conditional, BR7.4) | May share the same Lambda as `deliver-push`, branching on schedule name (logical-components.md notes either is valid); implemented here as a separate function for a cleaner IAM boundary — each function's role only ever needs its own narrow permission set. |
| EventBridge Scheduler group (`reminder-unit-schedules`) | Scheduling primitive | Dedicated group, not the account default; holds up to ~2000 active schedules at this app's 12-month ceiling (logical-components.md) | A separate scheduler-execution IAM role grants EventBridge Scheduler permission to invoke `deliver-push`/`auto-clear`, scoped to exactly these two functions — not a wildcard Lambda-invoke grant (security-design.md). |
| Secrets Manager — Firebase service-account credential | Secret storage | One secret per environment (`reminder-fcm-service-account`) | Referenced by `deliver-push`'s IAM role; never a plaintext environment variable or GitHub Actions repo secret. FCM was chosen (Q1) to reuse the Firebase project already established for Crashlytics (flutter-app-unit) — one unified API for both `DevicePlatform.IOS`/`ANDROID`, relaying to APNs automatically on iOS, avoiding a separate direct-APNs integration. |

## Shared Infrastructure

| Shared Resource | Owner Unit | Consumer Units | Access Boundary |
|---|---|---|---|
| `Post` DynamoDB Streams (Contract 8) | feed-unit | reminder-unit | reminder-unit owns its own Contract 8 handler's event-source-mapping/trigger configuration entirely; feed-unit is responsible only for enabling the stream with the correct `StreamViewType` (feed-unit's own Infrastructure Design). |
| `listPosts` (Contract 3) | feed-unit | reminder-unit (`myReminders`'s sync path enumerates new Event posts) | Read-only, via the shared AppSync API — no direct table access. |

No resource in this table is owned by reminder-unit and shared outward — both tables, all six Lambdas, and the EventBridge Scheduler group are exclusively this Unit's own.
