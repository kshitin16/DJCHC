## Q1. Backend-environment targeting: with the Amplify Hosting branch model, staging and production each have their own backend (own Cognito User Pool, own AppSync API, own tables), each described by its own generated `amplify_outputs.json`. A Flutter app build can only be pointed at ONE of them. How should the app know which backend it talks to?

- A. Flutter build flavors — a `staging` flavor and a `production` flavor, each bundling that Amplify branch's own `amplify_outputs.json` (Android application-ID suffix `.staging` / iOS bundle-ID suffix so both can be installed side-by-side on one device). Local development uses `ampx sandbox`, which writes a local `amplify_outputs.json` the developer's debug build picks up. The three files are git-ignored (they are environment-specific generated outputs, not source) and regenerated by `ampx generate outputs --branch <branch>` when needed. (Recommended)
- B. No flavors — a single build always points at production; local development uses `ampx sandbox` only, and staging is never exercised from a real device build
- C. A runtime environment switch inside the app (e.g. a hidden settings toggle) that loads one of several bundled `amplify_outputs.json` files
- X. Other (please specify)

[Answer]: B

## Q2. Firebase project layout for Crashlytics (the one non-AWS provisioning dependency NFR Design's `logical-components.md` named). reminder-unit's Infrastructure Design already decided to reuse this same Firebase project for FCM push delivery, so the layout chosen here serves both. How should the Firebase side be laid out across environments?

- A. ONE Firebase project, with separate app registrations per flavor — two Android apps (production application ID and the `.staging` suffixed one) and two iOS apps (production bundle ID and the staging one) registered inside the same project, so Crashlytics keeps staging crashes and production crashes separate while the builder manages a single Firebase console and a single FCM service-account credential (the one reminder-unit stores in Secrets Manager per environment). The per-flavor config files (`google-services.json` under `android/app/src/<flavor>/`, `GoogleService-Info.plist` per Xcode configuration) are committed to the repository — Firebase's own guidance treats them as non-secret app configuration (the API key they contain is restricted to the registered app IDs, not a credential), and committing them keeps CI/local builds reproducible without a secret-injection step. (Recommended)
- B. Two Firebase projects (one for staging, one for production), each with its own config files and its own FCM service account — stronger isolation, at the cost of two consoles and two credentials to manage
- C. One Firebase project with a single app registration per platform — staging and production crashes mixed together, distinguished only by the app version string
- X. Other (please specify)

## Q3. Release build signing and app-store distribution. Producing an installable release needs code-signing material (an Android upload keystore; an Apple Distribution certificate + provisioning profile, which in turn need a paid Apple Developer Program membership) and a store account on each side (Google Play Console, App Store Connect). For the first release, where should release builds be produced?

- A. Locally on the builder's own machine — `flutter build appbundle --flavor production` and an Xcode Archive, uploaded through the Play Console and App Store Connect/Transporter by hand. Signing material lives only on that machine (keystore file + `key.properties` git-ignored; Apple signing managed by Xcode's automatic signing). GitHub Actions does NOT build release binaries and holds no signing secrets. Simplest, zero CI signing setup, and fits a solo builder shipping a first release; automating this with Fastlane/GitHub Actions can be a later improvement once releases become frequent. (Recommended)
- B. GitHub Actions builds and signs release artifacts — keystore and Apple certificates/profiles stored as GitHub Actions encrypted secrets (base64-encoded), a macOS runner for the iOS archive, uploads to the store test tracks (Play internal testing / TestFlight) via Fastlane. Fully repeatable, but it is a meaningful amount of CI setup and secret handling to get right on day one, and macOS runner minutes are billed at a premium.
- C. A hosted mobile CI service (e.g. Codemagic) that manages signing and store upload through its own UI, keeping GitHub Actions for analyze/test only
- X. Other (please specify)

[Answer]: A

## Q4. Which Flutter test levels run in the GitHub Actions workflow? `team.md` (Q7) affirmed `flutter analyze` + `flutter test --coverage` blocking merge, and named `integration_test` for the higher-risk end-to-end flows (Google-federation sign-in, the admin gate, later the donation flow). Unit and widget tests run headless on a plain Linux runner; `integration_test` needs a real device or emulator, and the sign-in flow additionally needs a real Google account interacting with a browser-based OAuth screen — something that cannot be automated in CI without special test accounts and emulator plumbing.

- A. CI runs `flutter analyze` + `flutter test --coverage` (unit + widget tests, 80% line-coverage floor from the second Bolt) on a Linux runner, blocking merge. `integration_test` flows are run by the builder locally on a device/emulator against `ampx sandbox` before each production promotion — added as an explicit line item to the manual production checklist (`team.md` Q8), not automated in CI for the first release. (Recommended)
- B. Also run `integration_test` in CI on an Android emulator (GitHub Actions `reactivecircus/android-emulator-runner`), against a sandbox backend provisioned by the workflow — with the Google sign-in flow specifically excluded (it cannot be driven headlessly) and only the non-auth flows (Feed, Calendar, Suggestion submit with a pre-seeded test session) automated. Slower (several extra minutes per run) and needs AWS credentials in CI to spin up the sandbox.
- C. Skip `integration_test` entirely for the first release; rely on unit + widget tests only

## Q5. Follow-up — resolving a conflict between Q1 and Q2. You chose **no build flavors, production only** (Q1: B) but **one Firebase project with per-flavor app registrations** (Q2: A). Without flavors there is only one Android application ID and one iOS bundle ID, so only ONE Firebase app registration per platform is possible — a "per-flavor" layout cannot exist. There is also a practical consequence to settle: with a single app ID, a debug build running against `ampx sandbox` on your device reports crashes into the same Crashlytics stream as real production users unless collection is switched off for debug builds. Which way do you want to resolve this?

- A. Keep no flavors (Q1 stays B). One Firebase app registration per platform (Q2 effectively becomes C), and Crashlytics collection is disabled in debug builds (`setCrashlyticsCollectionEnabled(!kDebugMode)`) so local sandbox development never pollutes the production crash stream. Simplest; matches the single-target decision. (Recommended given Q1: B)
- B. Switch Q1 to build flavors (Q1 becomes A) so the per-flavor Firebase app registrations you picked in Q2 are actually possible, and a staging device build exists.
- C. Keep no flavors, but give DEBUG builds their own app identity via the debug build type only (Android `applicationIdSuffix ".debug"` on the `debug` buildType, a separate iOS Debug-configuration bundle ID) — a second Firebase app registration per platform for debug builds, so local-dev crashes land in a separate Crashlytics app without introducing full flavors. Lighter than flavors, but still two app registrations per platform to manage.
- X. Other (please specify)

[Answer]: A
